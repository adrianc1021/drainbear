# 「通渠」SEO／AEO 下一輪改善方案

**建議先修正可核實的內容風險，再補三篇文章的首頁正文入口及公司／施工證據。首頁剛完成的 title、方法、收費、案例及技術基礎應保留，先累積完整修改後數據。**

本輪是審查與方案，沒有改寫或部署公開網站。使用 SEO Audit、Vercel React Best Practices、OpenAI Playwright 的實際指引；另按業主要求安裝 TypeSafe skill。審查開始於 2026-10-13 香港時間，部分核對延續至次日。

## Executive Summary

- **最先做內容可信度修正。** 正式坐廁指南仍有「一次過斷症根治」；此外，文章程式會在缺少審閱人資料時預填「通渠熊渠務團隊」。應逐篇確認審閱紀錄，不能由預設值證明實際審閱。
- **補強三篇有服務需求的文章到首頁。** 坐廁自救、洗手盆去水慢及主渠／支渠責任文章，在主要正文未見直接首頁連結。保留各自資訊用途及個別服務頁入口，只在安排檢查的位置加入自然連結。
- **SEO 與 AEO 共用可信、可抓取內容。** 首頁目前 canonical、robots、H1、FAQ 同源資料、兩宗完工測試案例正常。Google 已停止 FAQ 富摘要；新增 schema 或 llms 檔案數量不是引用／排名保證。
- **模型與搜尋數據接入仍有明確缺項。** GSC Wizard 尚未在本對話出現工具；Jev API 回傳 403「Must supply an API key」。已保存安全憑證需求及可執行評估腳本，沒有編造最新排名或模型評分。

## 五項優先工作及驗收方式

### 1. 修正絕對效果聲稱，建立真正的文章覆核流程

**優先：立即；把握：高（文字及程式可直接核對）。**

相關頁面：[坐廁塞咗點算好？](https://drainbearhk.com/blog/toilet-clog-emergency-guide)。涉及「通渠、坐廁通渠、坐廁反覆淤塞、CCTV 照渠」的資訊。

正式原文仍寫：

> 坐廁反覆淤塞而搵唔到原因，可以要求 CCTV 照喉檢測，睇清楚係咪喉管移位或者有異物長期卡住，一次過斷症根治。

建議供渠務團隊覆核的替換：

> 坐廁反覆淤塞而原因未明時，可按入口、積水及鏡頭可達範圍評估 CCTV 照渠檢測。影像只反映可檢查位置的管內情況；是否需要疏通、拆裝或進一步工程，仍須按現場資料確認。

`blogRepository.ts` 的靜態文章 mapping 使用 `post.reviewerName ?? "通渠熊渠務團隊"`，並由文章頁輸出審閱欄位／reviewedBy。這個程式預設值不等於已有實際審閱；先與業主核對有無紀錄，缺少紀錄時移除預設審閱聲稱，保留真實撰寫單位及實際更新日期。對已確認人員與文章建立審閱名／日期／範圍資料，再輸出。

驗收：可見正文、文章列表／摘要、Article schema 及生成的 llms-full／knowledge 內容一致；沒有「根治」保證；原發布日期保留；技術文字有實際專業覆核。不要把有「不能保證」字眼的正確限制說明誤列作問題。

### 2. 補三條有上下文的首頁服務入口

**優先：下一小批修改；把握：高（正文連結缺口已抽查）。**

| 頁面                                            | 文章仍承接的搜尋意圖         | 建議放連結的位置／文字                                     |
| ----------------------------------------------- | ---------------------------- | ---------------------------------------------------------- |
| `/blog/toilet-clog-emergency-guide`             | 坐廁塞、沖水風險、需要師傅   | 處理未恢復或多處異常時，連「香港通渠服務及上門安排」至首頁 |
| `/blog/slow-basin-drain-causes-solutions`       | 洗手盆去水慢、隔氣／支喉問題 | 無法判斷堵塞位置時，連「通渠服務與檢查流程」至首頁         |
| `/blog/building-main-drain-vs-unit-branch-pipe` | 主渠或支渠、責任與管理處協調 | 安排檢查時，連「住宅與物業通渠服務」至首頁                 |

這些關鍵字是文章主題／意圖，不是本輪取得的新搜尋量或排名資料。原有首頁導覽、麵包屑與頁尾不是這次所指的正文入口；文章本來有個別服務入口時應保留，避免重複增加同一連結。

可審閱的三段文案：

1. 淤塞持續或多處同時異常時，可先了解通渠熊的「香港通渠服務及上門安排」，並傳送地區、受影響位置及安全拍攝的相片。
2. 未能確認問題在隔氣還是後段喉管，可先查看「通渠服務與檢查流程」，再說明已做過的處理。
3. 需要安排檢查時，可先了解「住宅與物業通渠服務」，並說明受影響單位及可用入口；涉及共用渠段時需先協調管理處。

驗收：每篇只加合適的一條首頁正文連結，三個文字均連 `/`；HTML 有真實 href、HTTP 200、保留原 canonical；電話及 WhatsApp 預填保持原文章情境；不改全部標題、不建立重複「通渠」著陸頁。

### 3. 補可核實公司及施工證據，準備真正的外部引用

**優先：現在收集，確認後發布；把握：缺資料狀態高，排名效果未可預測。**

相關頁面：`/about`、首頁及兩宗已發布完工案例。目標是讓「香港通渠公司、通渠師傅、通渠」的讀者能核對誰提供服務、做過甚麼及如何驗收。

公司頁現有品牌、電話、官方網站、Google 商家與 Instagram、服務範圍；未見營運公司與品牌的關係、可核實團隊背景或資格。請業主提供可公開佐證後，加入 About 與相同商家實體資料；沒有地址或客人上門安排資料時不要填造地址。

後續案例使用「問題→發現→方法→測試」，保留原相片／影片、工程日期與發布日期的區別。現有兩宗案例已符合部分要求，不再重複建卡；新紀錄才加新證據。CCTV 管內畫面與報告樣本、哪些管段未到達及交付方式，須待實際資料。

外部引用可由真實供應商、合作商戶、學校／物業的獲准工程分享開始，連到實際案例。Google 商家資料的名稱、電話、服務類別及接受查詢／到場安排應符合真實業務。自然搜尋與地圖排名分開量測，不能以服務範圍當成分店地址或距離優勢。

驗收：每個事實有來源及公開使用許可，Website／About／Plumber／官方商家一致；沒有捏造客評、年資或數量。今次沒有聯絡第三方、買連結、提交名錄或修改商家檔案。

### 4. 讓 AEO 答案有獨立語境及來源，不追 schema 數量

**優先：在內容覆核後整合；把握：格式可驗證，是否被引用需另行觀察。**

首頁、`/service-process`、收費指南及真實案例，組成可引用的答案來源。適合檢查的問題包括：香港通渠服務處理甚麼？收費如何確認？機械／高壓／CCTV 如何選擇？查詢前提供甚麼？反覆淤塞何時需檢查？

這些問題的主要資料已存在，不應再複製整段介紹。應檢查每個答案離開上下文後是否仍清楚：品牌／服務對象、問題、限制及下一步都能理解，並連至對應服務、流程或證據；固定錨點與實際修訂／專業覆核資料一致。只補缺少的語境，不擴張關鍵字牆。

重要官方更新：Google Search Central 明確記錄 FAQ 富摘要由 **2026-05-07** 起不再顯示；原 FAQ 文件現已導向停用公告。FAQ 可繼續服務讀者與結構化內容使用者，不能承諾 Google FAQ 富摘要。Google 的 AI 搜尋功能指引也表示沒有額外必要技術條件或特別 schema；基本可收錄、可顯示摘要及有用內容仍是基礎。

驗收：公開 HTML 可讀，FAQ 同源、答案來源可開啟，正文／JSON-LD／knowledge 一致；不得把 154 個答案目錄條目當成 AEO 分數，也不能把爬蟲 Allow 當成引用或排名成果。

### 5. 用 React 效能指引做下一個有量度的原型

**優先：內容小批完成後；把握：程式觀察高，節省幅度待量度。**

已完成的目錄拆分不用重做。上一輪同條件手機測試，LCP 中位數由 2.048 秒至 1.716 秒，JS 傳輸由 220,868 至 195,001 bytes；這是前一輪實驗室結果，今次沒有重跑速度測試，也不能證明速度造成排名變動。

現有可評估處：

- `App.tsx` 在整個公開頁面根部載入 tRPC／React Query／superjson；匿名首頁未使用登入查詢。先作 bundle attribution，再評估縮小 provider 邊界，避免延遲載入造成重新掛載、選項重設或查詢失效。
- `useCases.ts` 的元件掛載重新查詢可評估共用快取／請求去重，沿用已存在的工具，不為了 skill 示例盲目增加 SWR。
- `main.tsx` 用 createRoot 取代預渲染 DOM；可評估 bootstrap 已確認資料或 CMS 故障韌性，先量度內容是否閃動及資料回填，不能直接假定換 hydrateRoot 就安全。
- Google tag 現在按既有量測規則立即非同步載入。不要為少下載量直接推遲至互動，導致第一次 page_view／轉接量測遺失。

Vercel 指引中的 Next.js 專用 API 不直接套進 React／Vite。驗收要以同 URL、cache、viewport、CPU／網絡條件比較多次測試；保留首屏／正文／動畫／影片、電話、所有服務選項及 WhatsApp 轉接。真實用戶 CWV、INP 及排名因果需另外資料，不把建置警告當成故障。

## 各工具如何互相配合

1. **GSC Wizard**：取得可查詢的香港、完全相符「通渠」、按頁面及裝置切分的數據，提供決策與後續觀察基準。當前尚未提供工具，已停止新數據查詢路徑。
2. **SEO Audit**：辨識意圖、可信度、內部連結與技術基礎；中文不套英文字數門檻，不因多頁有同一字而合併／noindex。
3. **React Best Practices**：只針對實際可確認的下載、渲染與請求問題設計原型，保留業務流程。
4. **Playwright**：原始 HTML 與實際 DOM、JSON-LD、手機／桌面、收合錨點、電話／WhatsApp／影片與連結可抓取性驗證。
5. **TypeSafe／Jev**：用同一份已驗證證據，比較五個候選方案的「證據支持」及「現在可做程度」。它返回 typed Score／概率，並不是文字推理報告或 Google 排名預測；模型分數仍需人工覆核。

TypeSafe 已用 **一種方法**安裝：`npx skills add typesafe-ai/skills --skill typesafe-ai --agent codex --yes`。專案檔案是 `.agents/skills/typesafe-ai/SKILL.md`、LICENSE 及 `skills-lock.json`；沒有改 dependencies 或把憑證放進前端。

Jev 評估工具在 `/workspace/drainbear-seo-aeo-audit-2026-10-13/jev-evaluate.mjs`；`--prepare` 已成功輸出五個候選方案、十個獨立問題。它把權重及結果組合留在程式，檢查 typed response 與概率分布，沒有發布動作。實際推論尚未完成：API 回覆 403 缺少 API key；不能呈現假模型排名。

已在雲端設定草稿加入 `TYPESAFE_API_KEY` 憑證需求，目的地限 `api.typesafe.ai`，保留既有設定。請在環境設定安全提供值、儲存並發布環境；設定草稿保存不代表已套用。不要把 key 貼到對話。生效後可執行：

## 追蹤及決策條件

首次完整觀察期維持 **2026-10-14 至 2026-11-10**。Search Console 使用網頁搜尋、國家香港、查詢完全相符「通渠」，手機與桌面分開；看曝光、平均排名、點擊及顯示頁面，特別是首頁是否逐步承接服務搜尋。

前後比較必須使用相同國家／裝置／查詢篩選；不要拿未限定國家 69 次曝光當香港基準。GSC 的日期以來源報表設定為準，保留其時區及完整數據狀態，不擅自把每日資料轉成香港日界線。樣本不足再累積，不每日改 title。新一小批修正需記錄獨立發布日期，避免把所有變動當成一次實驗。

AEO 另用固定問題清單，記錄平台、模型、日期、是否啟用搜尋、語言／地區、回答中品牌是否出現、引用 URL 及回答是否符合事實。一般提及與有來源引用分開；推薦及答案會變動。Jev 的評分不等於其他 AI 實際引用；Search Console 也不能替代 ChatGPT／Perplexity 引用量。

電話點擊／WhatsApp 外跳不等於已傳訊息或客戶。未有已核對的實際查詢紀錄前，不推算客戶數或 SEO 收入。
